## Findings and acceptance checks

### F01 · P1 · Keep partial envelopes out of official history

A weekly `partial` envelope with a numerically valid snapshot can become last-good and a trend predecessor. The service excludes failed parents but admits both completed and partial parents into the same observations. It then calls `officialPoint` without requiring a completed parent. SQLite produced **last good 99 instead of 85** for completed 85 followed by partial 99. Adding a completed 90 after the partial produced **−9 instead of +5**. An earlier partial with a later observation time can also compete for the current headline after a newer attempt settles. [Observation admission](src/server/features/fleet/services/FleetService.ts#L114) · [Official history selection](src/server/features/fleet/services/FleetService.ts#L246) · [Official-point validation](src/server/features/fleet/services/fleetCalculations.ts#L59)

Carry the admitted parent into the observation record and require `observation.parent.status === "completed"` in the one official point constructor used by the headline, last-good and comparison. Keep partial observations eligible for the partial panel only. For the latest weekly terminal partial, show its own evidence or no evidence and report the previous completed score separately. Preserve the existing `observedAt <= completedAt <= now` checks and order good points by observation time. Re-run the 85 → partial 99 → 90 cases through the service, plus the snapshot-less partial and delayed completion cases already in the suite.

### F02 · P1 · Apply weekly series identity to both clocks

An explicitly diagnostic failed attempt with no weekly activity makes the weekly row unavailable. The service falls back from `latestWeeklyAttempt` to the latest terminal attempt of any series. Conversely, a weekly-tagged snapshot attached to a diagnostic parent can become a 99/A weekly grade. Both cases reproduced in SQLite. The null-series fallback also checks raw child rows and treats every case except all-diagnostic children as weekly, so unadmitted observations can affect classification and other explicit series can be misclassified. [Weekly selection and fallback](src/server/features/fleet/services/FleetService.ts#L192) · [Run-item series schema](src/db/fleet.schema.ts#L161)

Establish the weekly lane once from the parent. Accept weekly observations only from parents with a matching weekly identity. For legacy null parents, classify from a consistent admitted child series or migrate an independently known primary series. Null parents with no evidence stay unclassified. Keep the latest operational attempt in a separate DTO field if the preview displays it. The weekly disposition then receives `latestWeeklyAttempt` alone. Add isolated cases for diagnostic-only failure and partial, parent/child disagreement, and null parents with future, targeted or no children. A known weekly snapshot-less partial still displays `fresh_partial` with absent observation fields and a separate latest-attempt time.

### F03 · P1 · Verify the comparability fingerprint against the snapshot evidence

The comparison check verifies key shape and equality. It has no persisted inputs or producer binding that would establish the key's provenance. The helper generates keys with placeholder panel, applicability and profile values when inputs are omitted, and its current callers are tests. Matching hex alone cannot distinguish evidence collected on different panels or profiles. The response also collapses a method mismatch, missing prior point and observation gap into the same null trend. [Key builder and predicate](src/server/features/fleet/services/fleetEvidence.ts#L174) · [Trend calculation](src/server/features/fleet/services/fleetCalculations.ts#L283)

Persist a typed comparison descriptor or an immutable, verified reference to it on each snapshot. Require project/origin, rubric, actual panel and applicability hashes, collector and metric versions, lab profile including device/engine/region, and source scope. Build it from validated publication inputs with no defaults. In the reader, use `storedKey === computeVerifiedComparisonKey(verifiedDescriptor)` on each point before comparing. Compare only the immediately preceding completed graded point and return a reason when it fails. Keep the floor-to-floor display delta and retain the raw delta for evidence. Test 68 → 85 = +17, same presented digest with mismatched descriptors, each descriptor dimension changed independently, and an incompatible immediately preceding point between two compatible points.

### F04 · P1 · Use exact Rubric v1 arithmetic at the floor and reconcile the raw score

With technical, lab, schema, on-page, AI and links of `[20.23, 86.71, 44.57, 51.44, 26.44, 22.09]`, decimal calculation gives exactly **38.00**. The floating weighted sum gives **37.99999999999999**. The persisted 38/F record became ungraded at the SQLite overview boundary. Switching PostgreSQL to binary64 fixes storage rounding parity but preserves this calculation error. The reconciliation also accepts either a raw score or its floored integer with no explicit representation flag, so distinct composites in the same integer bucket can pass the same stored value. [Weighted sum and reconciliation](src/server/features/fleet/services/fleetCalculations.ts#L116)

Derive the score from exact rule credits and counts where available. If the persisted rubric deliberately defines a fixed decimal input scale, validate that scale on write and retain integer units or exact decimal strings. For two decimal places, `sum(pillarHundredths * weightPercent) / 10000` gives the headline by integer division, with the original numerator retained for raw comparisons. Use the agreed scale across both dialects and a shared canonical rubric definition. Persist one raw representation for new rows. Give any legacy floored representation an explicit version so it cannot pass as raw. Keep 89.9999999 below 90 wherever that precision is supported. Compute the fresh fleet median from canonical scores and format it for display at the end. The current service supplies floored scores and rounds the mean of the middle two, hiding half-point medians such as 84.5. Add golden tests for exact weighted integers, every grade boundary on either side, the 68 → 82 → 85 worked series, and reconciliation with an explicit contribution when the cap changes.

### F05 · P1 · Validate provisional evidence before publishing an interval

For 85% coverage, a persisted interval of `[-5, 200]` was returned verbatim by the overview. Otherwise the fallback assumes each measured pillar contributes its full pillar weight and substitutes zero for invalid values, then clamps the upper endpoint. Coverage alone does not establish how much of each pillar was observed. A second SQLite check showed an unavailable row returning an earlier partial interval while its coverage was null. [Interval builder](src/server/features/fleet/services/fleetEvidence.ts#L47) · [Overview DTO shaping](src/server/features/fleet/services/FleetService.ts#L277)

Persist the observed weighted mass and earned weighted contribution from admissible rule results, or derive both from those results. Validate `0 <= earned && earned <= coverage && coverage < 100`. For coverage 80–<100, compute `L = earned` and `U = earned + (100 - coverage)`. Apply the policy cap only after validating the uncapped interval. If compatibility requires reading legacy endpoints, validate their range, order and width against trusted mass or withhold them. Use the same current-evidence gate for coverage, pillars, interval and observation timestamp. Expose any deliberately shown stale evidence with its history label and time. Test `[73, 88]` at 85% coverage, a partially observed pillar, missing/invalid endpoints, coverage 79.99/80/99.99/100, a confirmed cap and a failed attempt over earlier partial evidence.

### F06 · P1 · Bind incident confirmation to independent evidence and preserve historical caps

The current parser accepts a legacy string as confirmation without a probe, intent record or timestamp. The JSON branch coerces two arbitrary values with `Boolean(...)` and has no independent probe identity or target scope. Its code allowlist also fails to distinguish provider/security blocking from a confirmed sitewide index block or critical render break. The same wall-clock 10-day gate revalidates historical scores. When a once-valid proof ages out, a 59/F historical point can disappear before the 21-day comparison window closes. [Incident evidence parser](src/server/features/fleet/services/fleetEvidence.ts#L6) · [Historical score cap](src/server/features/fleet/services/fleetCalculations.ts#L125)

Decode one versioned confirmation schema with strict literals and immutable references for the original failure, independent corroboration and expected production/index/render intent. Validate distinct probe identities and independent source or execution context, matching project/origin and required URLs/templates, eligible essential failure family, and probe freshness at observation time. Persist the verified decision with the snapshot. Compute current flags from incident freshness and resolution separately. Use the persisted observation-time decision for last-good and trend. Reject legacy self-assertions and unknown evidence, including provider blocking alone. Test a corroborated expected failure, duplicate probe, mis-scoped probe, missing intent, changed intent and an 11-day-old capped prior point. Check the score cap and the current incident count separately.

### F07 · P1 · Require a trusted approval for the exact import plan

The approval digest is optional and a caller-supplied label can become `approvedBy`. Even when present, the digest covers five roster fields but leaves out repo assignment, explicit aliases and states, and the project IDs resolved later. There is no trusted signer or pre-registered approval. The repository also contains a separate seeding method that writes without the CLI approval contract. The shipped JSON has 87 unique lowercase host strings, but the importer sets every member active with empty aliases and silently defaults invalid manifest fields. A count check does not establish roster lineage. [Approval parser and digest](scripts/import-fleet-roster.ts#L35) · [Project matching and write](scripts/import-fleet-roster.ts#L101) · [Parallel seeding path](src/server/features/fleet/repositories/FleetRepository.ts#L73) · [Manifest decoder](src/server/features/fleet/data/fleetManifest.ts#L22)

Make import a plan/apply operation. Resolve normalized hostnames, explicit canonical origin/aliases, enrollment policy and repo metadata using strict validation. Freeze exact stable member and project IDs, including nulls. Reject ambiguous active matches and require owner-approved changes for new mappings. Hash the canonical full plan, including tenant/version, and verify a trusted approval record or detached signature over that digest before any write. Derive approver and approval time from that record. Commit those exact rows atomically. Use one writer and handle same-plan concurrent retries as a success after re-reading the winning digest. A different plan for that version must conflict. Add process-level tests for missing or untrusted proof, changed metadata or project mapping, ambiguous project match, atomic failure, same-plan concurrent retry, and one successful approved import in isolated D1.

### F08 · P2 · Tighten publication identity and effective roster selection in both schemas

Both migrations enforce the non-null roster/project and run-item identities, and the snapshot index works for named series. Both allow multiple null-series snapshots for one item. Single-column FKs also admit relationships between a run and a member of another roster, or a snapshot carrying member/project values that disagree with its parent. The read path rejects bad run/snapshot lineage. The schema still admits it, and the existing integration fixture accepts either behavior. `getApprovedRoster` also picks the greatest timestamp without rejecting a future approval. SQLite selected a future empty roster instead of the effective roster with one member. [SQLite identity](src/db/fleet.schema.ts#L148) · [PostgreSQL identity](src/db/pg/fleet.schema.ts#L141) · [Roster selection](src/server/features/fleet/repositories/FleetRepository.ts#L48)

Make the publishable series identity non-null and define how legacy unidentified rows are quarantined before enforcing it. Pin rubric to the immutable run identity or include the validated rubric in the uniqueness key if one run item supports multiple rubrics. Add composite tenant/roster/member/project constraints where these IDs are duplicated, or derive them from a single constrained parent relationship. Filter effective approvals to valid UTC times at or before the shared dashboard clock and require an approved plan record. Assert duplicate and lineage rejection on insert in both replay suites, plus valid nullable _project_ assignments, independent named series, invalid and future approval clocks, and an unchanged migration generator result.

The DTO has no latest attempt timestamp or disposition totals, and the UI never renders `lastObservedAt`. Current lab, crawl and links can be scanned in the matrix. The other pillars require disclosure, which also gives no reason an unavailable trend is absent. [Repository fan-out](src/server/features/fleet/repositories/FleetRepository.ts#L177) · [Overview DTO](src/server/features/fleet/services/FleetService.ts#L31) · [Matrix row](src/client/features/fleet/FleetMatrixRow.tsx#L15) · [Design budget](DESIGN.md#44-performance-budget)

Use tenant/version joins in place of member-ID chunks. Select the needed latest weekly attempt, latest admitted weekly observation, last completed graded point and immediate graded predecessor via indexed candidates or a bounded read model owned by verified publication. Select candidates after admission and eligibility, so twenty partials cannot crowd out the last good point. Project only DTO fields. Assert query and row budgets on an 87-member fixture with realistic mixed history. Surface latest-attempt time and observation age separately, disposition counts, reasons for missing comparisons, and the six pillars at a glance or via an equivalent compact mobile view. For the preview, label unavailable run/provider/spend and cohort metrics explicitly if shown. The PRD's quartile and fixed-cohort summaries need the appropriate fresh-grade and named-checkpoint denominators before launch.
